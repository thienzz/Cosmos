## Architecture decisions

### State + engine plumbing
- **Zustand hot path via `setState()` direct**, not actions (Doc 27 §6.4). Plain `{x,y,z}` — not `THREE.Vector3` (not structurally cloneable).
- **`playbackSpeed = sim_seconds / real_second`** — resolved Doc 27 self-contradiction. 86,400× = 1 sim day/s.
- **`settingsStore` on localStorage now**; Dexie/IndexedDB adapter in T23. Same `zustand/persist` API, transparent swap.

### T38 ETL + catalog identity
- **`entities.ent_id` is NOT UNIQUE** — reverses Doc 25 §4.1 copy error. Doc 17 ent_id is a *subtype* label (ENT-7011 = globular cluster, shared by 29 Messier globulars); object-level uniqueness lives in `cross_identifications` via composite `(entity_id, catalog, catalog_ref)`. VARCHAR(12) width supports composite future refs ("ENT-NNNN:MNN") if we ever bundle them in the column, but default usage stays short.
- **Full-text search via trigger, not STORED column** — `to_tsvector(regconfig, text)` is STABLE (reads pg_ts_config catalog); Postgres `GENERATED ALWAYS AS (...) STORED` needs IMMUTABLE. `BEFORE INSERT OR UPDATE OF name, aliases` trigger using `'simple'::regconfig` is the canonical workaround + also better for proper nouns (no English stemming on "Andromeda"). Primary search path is still Elasticsearch; Postgres FTS is a fallback for ad-hoc queries.
- **`position_3d` auto-populated by trigger** — Doc 25 §4.1 declares the column but is silent on population. `BEFORE INSERT OR UPDATE OF ra, dec_coord, distance_pc` trigger calls `ST_SetSRID(ST_MakePoint(ra, dec_coord, COALESCE(distance_pc, 0)), 4326)`. Distance defaults to 0 (celestial sphere) when unknown so cone-search via ST_DWithin still works.
- **RA [0, 360) → ES geo_point lon [-180, 180]** — ES `geo_point` validates `-180 ≤ lon ≤ 180`. Astronomical RA is `[0, 360)`. Wrap in middleware + ETL at ingest time: `lon = ra > 180 ? ra - 360 : ra`. Canonical test: M13 at RA=250.4217° → lon=-109.5783°.
- **NAIF id priority > RA/Dec for solar bodies** — solar-system objects orbit, so a frozen ICRS RA/Dec is misleading. Ingest sets them NULL in Postgres (DEFAULT 0.0 because schema NOT NULL) + omits from ES. Search middleware exposes NAIF id as numeric `id` (not ES `_id` string). Frontend `SearchPanel.activateRow` priority: numeric id > ra/dec > stub. Solar bodies route through `SolarSystemRenderer.flyToEntity(naifId)` (live Kepler position); deep-sky routes through `flyToCelestialCoord(ra, dec, dist)` (direction-only, since no rendered mesh yet).
- **Coverage checklist is authoritative over CLAUDE.md count** — Doc 17 footer lines 14003–14010 count 31+27+15+20+14+19+12+16 = **154** subtypes. CLAUDE.md legacy "152" is off by 2 (prior double-count). Checklist + CI script use 154; CLAUDE.md gets updated when T48 closes.
- **Texture exceptions are explicit and narrow** — CLAUDE.md Rule #1 now lists 3 exceptions: skybox cubemap (original), Planck 2018 CMB sphere, SFD 1998 dust-extinction map. Both new ones are (a) scientifically irreproducible via procedural shader, (b) boundary-sphere static assets that don't affect the per-frame shader pipeline. Any other entity MUST render via procedural GLSL.
- **Live integration catches bugs unit tests miss** — ETL tasks ship with a mandatory live-smoke step (bring up real Postgres + PostGIS + ES containers, run migration + ingest + round-trip queries). T38 found 5 schema/wire bugs across Doc 25 §4.1 and Doc 26 §14 that all offline tests (pytest + `alembic upgrade head --sql` + mocked ES) had passed. Keep this gate in every ETL task from T39 onward.
- **Dev-only `window.__cosmosEngine`** — gated by `import.meta.env.DEV`. Preview-eval diagnostics without shipping globals.
- **`engineBridge` pub-sub for React → engine commands** — module-scope registry keyed by action name (`requestFlyToEntity`, `requestCancelFlyTo`). Last-writer-wins (one canvas = one engine). No refs threaded through React tree.
- **`userData.naifId` on every pickable mesh** — Raycaster returns intersection → O(1) catalog lookup. No scene-graph walking each frame.
- **Hover throttled to 100 ms** (Doc 27 §6.3) — raycasting is cheap, React re-renders are not.

### Rendering
- **THREE.Points over InstancedBufferGeometry** for stars — 1 draw call with simpler shader. Instanced-quad upgrade deferred to T26 if point-size caps bite.
- **Two planet frag shaders, not eight** — `planet-rocky.frag` + `planet-gas.frag`, body selected via `#define PLANET_*` (compiler dead-code-strips).
- **Planet palette in `utils/planetPalette.ts`, NOT shaders** — tints are uniforms. Lets jsdom tests assert ΔE76 by reading uniforms.
- **Sun direction is a uniform, not a `DirectionalLight`** — shaders consume `u_sunDir` directly. Quality tiers don't reason about GPU lights.
- **Saturn ring radii in parent-radius units** — same shader works at any world scale. Cassini Division = `discard` between `u_outerB`/`u_innerA`.
- **Shaders: `u_/v_/a_` prefix + `@param` docs**; omit `#version 300 es` (Three.js prepends for `glslVersion: GLSL3`).
- **`vite-plugin-glsl` `#include`** drives shared `lib/noise.glsl` + `lib/lighting.glsl`. `warnDuplicatedImports: true`.
- **Skybox: dominant-axis face selection** — each S² point lands on exactly one face. No seam logic.

### Scale + physics
- **Kepler solver = Danby quartic-convergence** — stable to e ≈ 0.9999 in ≤30 iterations.
- **T14 display scale, not Doc 23 1:1 km** — `orbitScale = 12 units/AU`, `bodySizeScale = 0.000_02`, Sun log-clamped to [1.2, 2.2]. Strict 1:1 ships with T23.
- **`?demo=solarsystem` auto-starts at 1× (REAL-TIME), not 2.6M×** — T14 kicked off at ≈1 yr / 12 s so orbits visibly moved on load; swapped back to real-time so T18 fly-to targets don't drift out from under the camera mid-animation and the "live data" feel survives. Users wind up speed via the TimeControls slider when they want a laps-per-second demo.
- **Moon orbits parent-relative-inflated** — outermost moon at 6× parent visual radius. At true scale moons are invisible next to planets.
- **Retrograde via `i_deg > 90°`**, not negative period — matches Doc 23 §8.5 (Triton's 156.865°).
- **Minor bodies = orbits only, no meshes** — 260 deterministic asteroid/KBO stubs clear TS-DATA-003's ≥290-body target. Instanced points ship T23.
- **Galactic matrix = Doc 23 §2.2 7-digit truncated** — 10⁻³° residual. Reid & Brunthaler upgrade in T26.

### Selection + fly-to UX
- **Click-vs-drag discriminator @ 4 px** — orbit drag + picking both on LMB. Pointerup travel ≤4 px = click (matches OS double-click drift).
- **Fly-to ease = smoothstep cubic** — zero derivative at both endpoints so camera starts/ends at rest.
- **Bezier perp = (away − (away·segment)·segment).normalize()** — first pass used `away = midpoint − avoidPoint` directly; collinear obstacles collapsed the bulge. Project out segment component for robust orthogonal perp.
- **Fly-to parent-aware approach direction** — default `start − end` heuristic could put Sun between camera and planet at display scale. Fix: `approachDirection = −unit(body − parent)` so camera lands on lit hemisphere with parent safely behind. `dot(forward, toSun) = −1` for planets.
- **Fly-to freezes end target at start** — at 2.6M× demo playback planets orbit away mid-flight; T20 tracking now solves this for selected bodies.
- **`fly-to duration` defaults to log-scaled `computeFlyDuration`** — Doc 19 §4.2, base 2.5 s clamped [1.5, 4].
- **Escape priority: cancel > close** — while `isTransitioning`, Escape cancels; otherwise closes info panel.
- **InfoPanel = Doc 24 S-3.0 (Compact)**, not S-3.1 (Full). Full-panel + Doc 22 toggles ship T28-ish.
- **`bodyToEntity` synthesises `EntityData` client-side** — T18 HTTP swap is transparent. `id` = NAIF id until backend assigns catalog ids.

### WebSocket manager (T22)
- **Dispatcher busts HTTP caches, listeners only react** — `data_version_update` is Doc 27 §7.2's canonical invalidation signal. Doing the cache-bust inside the dispatcher (before calling user `onDataVersionUpdate`) means every consumer of the cache (entity LRU, autocomplete LRU, ETag store) is flushed in one place; listeners only get to handle the "tell the user" side-effect. Belt-and-braces: we call `clearEtagCache()` explicitly even though `clearEntityCache()` already calls it, because a future tile/search consumer might rely on a cleaned ETag map without going through the entities module.
- **Push frame as a live override, not a cache splice** — the `ephemeris_push` arrives at the client's currently-simulated epoch (the server's answer to a `time_update`). We store it as `livePoint` with a short tolerance window (0.5 days default). Inside the window: `sample()` returns the exact push position (zero interp error). Outside: it drops through to cubic interp, then Kepler. Splicing into the `Float64Array` cache would corrupt cubic neighbours on nearby queries and require cache-index math to place the sample; the override is simpler, cheaper, and auto-expires.
- **Throttle gate stays in front of the override** — even with a push frame cached, if the user scrubs at 1e9× the cache would churn past the override's tolerance in one frame. We keep `maxPlaybackDaysPerSec` as the outermost guard so high-speed playback never reads stale push data. Cost: a freshly-pushed body at 1e9× speed still gets Kepler. Acceptable — at 1e9× the user wants raw animation speed, not sub-km accuracy.
- **Construct WS but don't auto-connect** — SceneManager builds the CosmosWebSocket unconditionally (so `data_version_update` cache-busts work across any demo), but `connect()` is opt-in via `autoConnectWebSocket: true`. Dev without a live backend would otherwise spin in the reconnect loop, burning the backoff cap every 30 s. Real auth / session flow (post-T36) will flip the default.
- **TimeEngine stays on WebSocketLike** — we could have ripped out the `{ send(string): void }` interface and had TimeEngine call `cosmosWs.sendTimeUpdate` directly. We didn't: that would break the 12-test T11 EphemerisPushDispatcher suite that still drives `sendTimeUpdate(mockSocket, …)`. Instead SceneManager hands TimeEngine a tiny adapter `{ send: (raw) => cosmosWs.send(JSON.parse(raw)) }`. One round-trip JSON per slider tick — trivial cost, zero test churn.
- **Fan-out to the T11 dispatcher, not replace it** — `applyEphemerisPush` both updates the sampler and re-serialises to feed `timeEngine.handleWebSocketMessage(raw)`. The old dispatcher still works (tests still pass), and new consumers (UI push-indicator, analytics) can subscribe via either the SceneManager's listeners or the raw dispatcher.
- **Heartbeat interval = server-close interval / 2** — Doc 26 §14.4 says the server closes after 60 s of silence. 30 s ping keeps us one missed heartbeat away from disconnect (jitter-tolerant without being chatty). The pong path is a no-op in T22 — T35 observability will tap it for round-trip latency.
- **Normal close (1000) still reconnects unless it's a `dispose`** — Doc 27 §15.3 treats WS drops uniformly. A 1000/"dispose" pair is the client's own shutdown; anything else (including the server sending 1000 "shutdown for deploy") is a reconnect. `disconnect()` flips `autoReconnect=false` BEFORE calling close so the `onclose` handler's reconnect path is inert.
- **Fake-socket test pattern** — a plain object implementing `WebSocketAdapter` is enough; no need to extend `EventTarget`. Push `.instances` onto a module-level registry so tests can grab "the socket the manager just created" without threading handles through every call. `simulateOpen/simulateMessage/simulateClose` helpers make intent obvious in the test body.
- **Preview-eval module-instance gotcha confirmed again** — `eng.webSocket` is the app's live instance; `import('/src/api/index.ts').CosmosWebSocket` in eval is a SEPARATE class. Fake-socket dispatch test had to use the eval-local class and verify its own listeners fire; the app's live dispatcher was NOT exercised from the eval. For smoke tests that need to exercise the app path, call the listener-downstream primitives directly (`eng.ephemerisSampler.applyPushFrame(...)`, `eng.solarSystem.update(...)`) — those ARE the app's instances.
- **`dispatch` stays private, `applyPushFrame` is the test surface** — we never exposed a `simulateIncomingFrame` backdoor on CosmosWebSocket. Unit tests drive `fakeSocket.onmessage?.({data: …})` directly; preview smoke drives the sampler directly. No production-only escape hatches.

### Tile streaming (T23)
- **Priority queue = sort-then-shift, not a proper heap** — the queue's working-set size is bounded by the manifest scope (≤ a few thousand pending tiles even at the galactic regime), so an O(n log n) sort per `pump()` is trivial next to the network cost. A real binary-heap buys us nothing measurable and costs a test surface. Revisit if profiling ever shows `pump` in the flame chart.
- **Pre-evict on write, not post-write** — `recordLoaded` checks `projected > budget` BEFORE calling `markTileLoaded`. Alternative was to write-then-evict, but that briefly lets `gpuMemoryUsedBytes` exceed the budget, and any observer (`useStore` subscriber on the tile store) would see a transient overshoot. Pre-eviction keeps the invariant `used ≤ budget` always true.
- **Disk writes are fire-and-forget** — `diskCache.put(...)` returns a promise we drop with `.catch(() => undefined)`. Rationale: the tile is already in the in-memory store, so the render path doesn't care about the durable write. If IDB is full / private-mode / quota-exceeded, the app degrades to "no offline" silently; it keeps going.
- **Dexie dual-write settings adapter** — zustand's `persist` calls `getItem` synchronously during first render. Pure Dexie would return a promise that resolves AFTER first paint, so the UI would flash the default settings. Strategy: write to BOTH localStorage (sync) and Dexie (durable) on every change; read from Dexie first (authoritative), fall back to localStorage. On a fresh install the first read returns `null` either way → defaults apply → first `setItem` populates both. On a warm start Dexie wins. Migration from T04's pure-localStorage persistence happens transparently on the next write.
- **TileDiskCache fallback on missing IndexedDB** — `getDb()` returns `null` when `typeof indexedDB === 'undefined'` (SSR, ancient browsers, some iframe sandboxes). Every method then returns the "no-op" shape: `get` → `null`, `put` → `{ stored: false, evictedBytes: 0 }`, `stats` → zeros. The streaming manager treats a null get as a cache miss and falls through to network. No feature flags, no throw.
- **Manifest version stamp on disk writes** — `diskCache.put(address, version, buffer)` captures the manifest version at write time. When `data_version_update` fires, `keepOnlyVersion(newVersion)` (or `clearVersion(oldVersion)`) sweeps stale tiles in one WHERE clause instead of individually revisiting each in-memory entry. The WS dispatcher already flushes the HTTP caches; a future hook here will flush the disk cache on the same frame.
- **WS URL → manifest address normaliser** — server sends `/v1/tiles/stars/5/128/64/3`; manifest uses `stars/5/128/64/3` (with no `tiles/` prefix after `starTileUrl()`). `tilePriorityHintsFromWsUrls` strips scheme + host + `/v1/` + `tiles/` so the priority lookup keys match manifest keys. Also tolerates already-bare addresses (e.g. from an in-process cull worker).
- **attachTileStreaming default-on, but fetch path is inert without manifest** — tests that boot SceneManager don't hit the network because nothing enqueues tiles until either (a) WS `tile_priority` arrives, or (b) a future frustum-cull worker pumps hints. So the default `true` is safe; tests that need a narrower scope pass `attachTileStreaming: false`.
- **Preview smoke pattern for TSM** — per-module-instance gotcha strikes again: `import('/src/engine/TileStreamingManager.ts')` in preview_eval returns the eval-local class, not the SceneManager's instance. So we spawn a *new* manager with a mock fetcher + mock disk to exercise the happy path end-to-end. For the app's live manager, we drive the WS listener directly (`ws.listeners.onTilePriority({...})`) and watch the live tile store for state changes.

### Star-tile streaming end-to-end (T26)
- **Encoder lives in `@cosmos/tile-decoder`, not a sibling `@cosmos/tile-encoder`** — pure functions with no Node deps, usable from both the ETL seeder (Node) and in-browser test fixtures without a second workspace package. Worth revisiting if the encode path ever grows Node-specific hot loops (xxh3 checksum, zstd compression) — then spin it out.
- **`.js` import suffix on new files only** — existing tile-decoder src doesn't use `.js` extensions and relies on `moduleResolution: bundler` inside Vite/Vitest. My new encoder source uses `.js` suffixes so the compiled `dist/` output runs under Node ESM resolution for the ETL script. Existing files stay unchanged (touching them would be a broader migration).
- **Seed-time distribution, not Gaia ingest** — T26 uses a Mulberry32-seeded IMF generator with 12 real bright stars injected by ICRS position. Burn-in of real Gaia DR3 is a later ETL task; the seeder output is byte-identical across runs (deterministic for reproducible fixtures + smoke tests) and is sufficient to exercise the end-to-end pipeline. Sirius et al. get their real positions + magnitudes so visual-QA / search tests hit truth.
- **4×4 central block at z=1, not a full 8×8 grid** — the octree spec allows x,y ∈ [0, 8^z) at each depth, but populating all 64 cells would leave 48 addresses with ≤10 stars each (most of the near-Sun population sits inside ±100 pc in XY). I populate only the 4×4 block covering X,Y ∈ (−100, +100) pc, 16 tiles × ~6 250 stars each. The other addresses are genuinely empty → Rust tile-server returns 404 `TILE_NOT_FOUND` per spec. T28+ can extend if needed.
- **`sceneUnitsPerPc = 500` display scale, not 1:1 parsec→km** — the strict scale flip was originally scoped into T26 but requires a broader camera/fov/depth refactor that's out of proportion to the rest of this task. 500 u/pc puts Sirius at 1318 scene units — well beyond the T14 solar-system volume (Neptune ≈ 360 u at orbitScale=12) but still inside the controller's widened `maxDistance=250 000`. Flip happens in one spot when the full strict-scale task lands.
- **One `THREE.Points` per tile, not a single merged geometry** — future viewport-culling worker needs to add/remove tiles independently, so per-tile Points lets us dispose a tile's GPU buffers on eviction. Draw calls at stellar regime = #mounted tiles ≤ ~32 at the peak populated LOD, still well under the 500-call budget. Instanced-billboard upgrade can happen later as a `StarPointMaterial` swap.
- **Baked ICRS→scene permutation in positions, not a group rotation** — Three.js +Y is up; ICRS-ecliptic +Z is up. We bake `(X, Y, Z) → (X, Z, −Y)` into the `position` attribute at upload time so the vertex shader stays identity. No per-frame matrix cost, no rotation hierarchy to reason about when the picker / raycast probes hit a tile.
- **`sceneUnitsPerAU` still 12 in T25 regime input** — the T25 regime controller gets `distanceAU = distanceScene / 12` per the T14 solar system's orbitScale. The star-tile scale (500 u/pc) is independent — stars live at distance_pc × 500 scene units but the regime controller computes in AU space using the solar-system scale, which is what Doc 27 §9.2's thresholds (500 AU, 1 kpc, 1 Mpc) are expressed in. Separation of concerns: tile render scale ≠ regime-input scale.
- **Camera parked at (0, 4000, 15000) + `setDistanceClamp(1, 250_000)` on starfield boot** — pulls camera to a stellar-regime pose immediately (so the T25 initial regime is `stellar`, no transition needed to admit star tiles). Widening the camera controller's distance clamp is required because the default maxDistance=1e5 would deny wheel-zoom reaching the 100-pc fringe of populated tiles (at 500 u/pc → 50 000 units radius).
- **Dev Vite middleware serves `data/tiles/` → `/v1/tiles/*` in development** — `?demo=starfield` smoke test works without the Rust tile-server binary running. Manifest gets envelope-wrapped on the way out to match Doc 26 §2.5; binary tiles ship raw with `X-Tile-Version` + `Cache-Control`. Delete when tile-server is bundled into local Docker Compose.
- **Manifest addresses carry no `stars/` prefix; streaming-manager addresses do** — Doc 26 §7.4 specifies the manifest's `address` field as `"1/3/4/0"` (kind-namespaced by the parent `stars:` object). The `TileStreamingManager` keys addresses with the `stars/` prefix so the T25 regime filter (`tileKindFromAddress`) can classify them. SceneManager's bootstrap glues: `stars/` + manifest address → streaming-manager key; on `onTileLoaded(address, buffer)` the renderer stores the same namespaced key.
- **Tile count sanity metric: `starTileField.getStarCount()` at smoke-test time** — verifying `renderer.info.render.points` includes the legacy T08 starfield + skybox dots + star-tile Points, so it's a loose bound. ### Exotic object shaders (T28)
- **One frag per kind, not unified `#define`** — same call as T27 nebulae. Black hole, pulsar, and magnetar diverge at the first sample (horizon distance test vs beam cone vs field-line cylindrical tubes); packing them into an `#ifdef EXOTIC_*` frag would leave ~70% dead code per permutation and the TS-VQA-006 ΔE assertions would be unreadable. Three small focused frags beat one monolithic one; the vertex shader + `lib/volumetric.glsl` + `lib/noise.glsl` still share.
- **Black hole as composite raymarch, not geometric ensemble** — the "textbook" way to render a black hole is separate meshes: an opaque sphere for the horizon, a thin disc for accretion, two cones for jets, plus a post-process lensing pass. I packed all four features into a single cube raymarch instead, so transparency ordering is composed in-shader (horizon early-terminates accumulation; jets and photon ring alpha-blend in front). Two wins: (a) the render is one draw call per black hole instead of ~4 — galaxy-scale ENT-6011 rendering later won't thrash draw calls; (b) the disk/jet/horizon never Z-fight because they all write a single fragment with composited alpha. Trade-off: no geometric ray-tracing of the lensing effect (the "bright curl above the horizon" is faked with a thin photon-ring emission band rather than a true Schwarzschild geodesic). Full geodesic lensing is a post-process job for T30 where we can afford a fullscreen quad.
- **Horizon as opaque early-terminate, not sphere geometry** — inside the raymarch, the horizon test sets `accumAlpha = 1.0` and breaks. This means anything between the camera and the horizon (accretion disk front half, photon ring approaching side) is correctly composited in front, while the horizon occludes the back half of the disk and the far jet. Tried it with just `accumColor += black × (1-alpha)` without the early-break first; visible artefacts because subsequent march steps still accumulated non-zero emission *behind* the (already-opaque) horizon and the back-face front-to-back composite added their colour on top. Early-break is the only correct way.
- **Disk as tilted toroid in the cube frame, not a rotated mesh** — applied the disk tilt (`u_diskTilt`) inside the shader via an X-axis rotation in `toDiskFrame`, not on the `mesh.rotation`. Reason: the raymarch AABB is the local unit cube; rotating the mesh would break `cosmos_rayAabb`'s `[-1, 1]³` bounds assumption. Shader-frame rotation keeps the march bounds intact while letting the disk freely tilt within them.
- **Pulsar magnetic axis is time-varying, rotation axis is fixed** — rendering the pulse sweep as a uniform rotation of the whole material would require rotating the BoxGeometry or the camera frame, both of which break worldToLocal. Instead: `magneticAxis(t)` is computed per-fragment per-frame, tilted off +Y by `u_magneticTiltRad` then rotated around +Y at `u_pulseFrequency`. The beam cone test is `dot(p/|p|, magAxis) > cos(beamHalfAngle)`; because `magAxis` changes each frame, the beam visibly sweeps across fixed fragments (the lighthouse effect). Zero mesh-transform churn.
- **Beam bipolar test via `max(dot(+axis), dot(-axis))`** — naive version was two separate `beamEmission(+axis) + beamEmission(-axis)` calls, 2× the shader work per sample. Folded into one max(): `max(dot(dir, ax), dot(dir, -ax))` picks whichever beam the sample is closer to. Same visual result, one cone test per sample.
- **Magnetar field twist via `φ' = φ + y × twist`** — cheapest way to turn a dipole pattern into a Doc 22 helical-winding pattern. Compute cylindrical coords (ρ, φ, y), shift φ by a y-dependent term, then use `cos(φ' × N)` for tube count. No geometry, no extra samples, just a 1-line transform. Result is indistinguishable from a real 3D helical B-field at the resolution of a 48-step raymarch — the twist is what makes the magnetar visually distinct from the pulsar's clean dipole.
- **Reconnection hotspots via grid cell hash, not particle system** — Doc 22 ENT-8010 wants "~8–12 hotspots" placed stochastically and pulsing independently. Implementing this as a particle system would mean 12 lights per magnetar, extra draw calls, CPU animation. Instead: the cube is partitioned into a grid (`floor(p × density)`), each cell gets a random hash, cells with hash>0.78 become potential hotspots. Each hotspot's pulse phase comes from a second hash of the cell. Zero CPU state, zero extra geometry — the stochastic placement emerges entirely from the spatial hash. ~22% of cells become hotspots at density=8 → ~12 hotspots per cube, matching the Doc 22 spec.
- **Disk temperature gradient in 3 bands, not 4 stops** — Doc 17 ENT-1032 palette is "inner white, mid yellow-white, outer yellow-orange, coolest red" (4 regions), but the colour transition between the yellow-white and yellow-orange is so subtle that reading the shader is easier with 3 named regions (white / yellow / orange). If a future tuning pass needs the fourth band it's a one-line addition to `diskColour()` — the uniforms don't need to change.
- **Preview smoke for exotic: camera local matches expected from mesh world** — preview rAF throttles to ~2 fps headless (T13 / T21 / T27 gotcha), so FPS isn't meaningful. Instead verify correctness via the uniform: pulsar mesh at world (0, 0, -42), scale=6, camera at (0, 6, 60) → expected `cameraLocal = ((0-0)/6, (6-0)/6, (60+42)/6) = (0, 1, 17)` ✓. Draw calls stay at 5 (3 exotics + skybox + starfield). TS-VQA-006's "≥30 FPS" is a real-GPU check — at 48 triangles + 5 draw calls we're trivially under the 500-call / 1.5M-tri budget.
- **Params held in palette module, not hard-coded in shader** — same separation as T27 nebulae / T13 planets. Tests read `BLACK_HOLE_PARAMS.diskInnerRadius` etc. from the TypeScript module; the shader only sees uniforms. Flipping to Doc-accurate ISCO geometry (2× r_s vs Doc 18's 6GM/c² = 3× r_s) is a one-line edit in `exoticPalette.ts` without touching any .frag.
- **Flare intensity as uniform, defaults to 0** — Doc 22 ENT-8010 giant-flare toggle is "off by default, triggered manually". A uniform-valued multiplier lets the T-future UI toggle layer crank `flareIntensity` to 1.0 for the flare animation; at 0 it's inert (no additional fragment work). No conditional sampling / dynamic branching / permutation #define — just a multiplicative gain.

### Nebula volumetric shaders (T27)
- **One frag per kind, not a unified `#define` shader** — the five nebulae diverge on their very first line (emission raymarches fbm + emissive palette; reflection raymarches scattering off an external star; dark integrates absorption into a pre-multiplied-alpha blend; planetary + supernova sample geometric shells, not fbm density). Packing all of this into `#ifdef NEBULA_*` would leave every permutation with 80% dead code and make the TS-VQA-003 ΔE assertions unreadable. Five small focused frags beat one monolithic one; the vertex shader + `lib/volumetric.glsl` still share.
- **Model-space raymarch against the unit cube** — fragment shader's ray-AABB uses `[-1, 1]³` and the vertex shader exposes `v_modelPos` from the raw `position` attribute. That means the geometry MUST be `BoxGeometry(2, 2, 2)` and sizing is done via `mesh.scale`. Initial instinct was to parameterise `BoxGeometry(size, size, size)` and feed `size` into the raymarch bounds — tried that first, got invisible nebulae because the shader marched `[-1, 1]` inside a `[-6, 6]` geometry and every `cosmos_rayAabb` test missed. Picking a single canonical AABB and letting `worldToLocal` handle the scale is the cleaner invariant.
- **CPU-side `u_cameraLocal` per frame, not `inverse(modelMatrix)` in GLSL** — `NebulaMaterial.update(dt, elapsed, cameraWorld, meshMatrixWorld)` runs a single `Matrix4.invert` + `Vector3.applyMatrix4` per nebula per frame. Doing the inverse on the vertex shader would re-run it for every one of the 24 cube vertices, and you still have to upload the camera position as a uniform anyway (or chase it through `cameraPosition`). Keeping it CPU-side also means the same code path works with rotated / non-uniformly-scaled nebulae for free (tests cover the rotated case).
- **Dark nebula = pre-multiplied-alpha replace, not a second pass** — Doc 18's prescription is "subtract stars behind," which in a forward-rendering pipeline normally requires a second pass or an off-screen framebuffer sample. We cheat by emitting `fragColor = vec4(dustTint * extinction, extinction)` with standard `NormalBlending` — the dst multiplier is `1 - srcA`, so at full extinction the destination is zeroed and the dark dust tint shows through. At partial extinction the background is attenuated proportionally, which is exactly the absorption behaviour. One pass, no framebuffer trick, visually faithful.
- **Emission palette via 4 weighted Gaussians, not step-function classification** — early draft used `if (d > 0.7) haColor; else if (d > 0.4) oiiiColor; ...`. Produced hard contouring bands visible at any camera angle (the isosurface between SII and OIII showed up as a sharp edge). Replacing the if-tree with four Gaussians centred on the 4 density "signatures" (0.15/0.30/0.50/0.80) — weighted-summed into `emissionColor` — gives continuously blended narrowband colours. Cost: 4 exp() calls per sample. Budget: trivially fits in the 64-step raymarch.
- **Log-depth `gl_FragDepth` in every nebula frag** — the T13 planet fix (CLAUDE.md gotcha re `USE_LOGARITHMIC_DEPTH_BUFFER`) applies identically here: without the per-fragment log-depth write, the nebulae test against non-log depth while the star-point / solar-system shaders test against log depth, and the nebulae would occlude whatever is behind them (including the Sun when the camera's inside the solar-system). Every frag emits the `log2(vFragDepth) * logDepthBufFC * 0.5` line guarded by the ifdef.
- **`DoubleSide`, not `BackSide`** — BackSide alone invokes the fragment only when the camera is outside the box looking in. When the camera enters the AABB (user flies INTO a nebula), BackSide's culling hides the nebula entirely. DoubleSide renders both faces; the front face provides the entry ray when outside, the back face provides it when inside. Because `depthWrite: false` and the raymarch clamps tNear to 0, double-invocation on the same pixel is harmless (both instances produce the same accumulated colour).
- **TS-VQA-003 ΔE76 round-trip via `Color.convertLinearToSRGB`** — Three.js r184 stores `new Color('#FF3333').r` in linear space (≈0.033 for the green channel, not 0.2). `deltaE76` / `rgbToLab` expect sRGB-coded 0–1. First test pass compared linear vs sRGB and ΔE came out at 30+ on the planetary shell colours. Fix: `c.clone().convertLinearToSRGB()` before the deltaE call. Keeps the render path untouched (shaders consume the linear value as Three intended for physically-correct blending) while making the test assertions semantically correct.
- **Mesh `updateWorldMatrix(true, false)` before the uniform write** — `mesh.matrixWorld` is only refreshed inside `renderer.render(...)`. If we read it before render, we get the previous frame's matrix. `updateWorldMatrix(true, false)` (first arg = walk up to root, second = don't descend) forces the refresh so `u_cameraLocal` and the vertex shader's `modelViewMatrix` agree on the same frame's transform. Two tests specifically cover the rotated + translated case to lock this in.
- **Preview smoke validates both raymarch correctness and palette selection** — `window.__cosmosEngine.nebulaGallery.getHandles()[0].material.uniforms.u_cameraLocal.value` surfaces the exact value the shader sees; `renderer.info.render.calls = 7` (5 nebulae + skybox + starfield) confirms no material compilation rejected; the screenshot confirms each kind renders a qualitatively distinct pattern. The expected "emission goes red, reflection goes blue, dark goes silhouette, planetary shells cyan/orange/red, supernova synchrotron blue" all present.

### Accessibility (T33)
- **Two live regions at document root, not per-component** — Doc 16 §Live Regions describes `aria-live` announcements. First instinct was to attach a live region inside each panel (InfoPanel, TourNarrationPanel, etc.); problem: some state (mode switch, scale regime) has no natural owner panel, and attached-inside-panel regions get torn down when the user closes the panel — losing the announcement before the reader speaks it. Fix: one polite + one assertive region mounted to `document.body` by the lazy singleton, writable from anywhere via `announce(msg, priority?)`. Survives any React unmount. Stays quiet (empty text) when no announcements are active so SR's don't announce a "live region added" event themselves.
- **Clear-then-rewrite debounce (10 ms), not direct write** — writing the same string twice in a row into an `aria-live` region doesn't always re-announce (no mutation record — the text is equal). Clearing first + scheduling the actual write via `setTimeout(..., 10)` forces a fresh `childList` mutation. Cost: a ~10 ms delay on the SR speaking. Benefit: repeat actions (same body clicked twice, same tour step re-entered) re-announce reliably. Alternative was cycling through a pool of regions, which is heavier for the same net outcome.
- **Hook-based store subscription, not effect-per-store-change** — `useAriaAnnouncements` wraps four Zustand `subscribe` calls in independent `useEffect`s, each with `lastX` ref dedupe. React's render cycle would have rebuilt the subscription on every render otherwise. Refs (not state) because announcement emission is a side effect, not something React needs to render off of.
- **Priming happens inside the effect, not on first render** — `lastMode.current = useModeStore.getState().activeMode` is set synchronously inside the `useEffect` body before returning the subscribe cleanup. If we'd primed in the ref's initializer at render time, the store might not have finished hydrating its persisted state yet (Dexie is async on first load), and the first announcement after mount would wrongly fire for the initial value.
- **Clear-selection stays quiet** — every other a11y stack I looked at fires "selection cleared" on `clearSelection`. Rejected: the user is almost always closing a panel they already know is there; hearing "selection cleared" every time Escape is pressed is noise. Selections only announce on *set-to-new*, not set-to-null. Tour exit IS announced, because that's a mode transition, not a dismissal.
- **`useReducedMotion` / `useHighContrast` are one-way from OS → store** — the hooks never read the store's value and apply it to the OS (obviously impossible), but they also never "freeze" the store after the first OS seed. If the OS flips mid-session (user toggles system accessibility settings), the store re-syncs. Separate "user has explicitly overridden" state would require a 3-way toggle (`auto / on / off`) in the panel — deferred. Current behaviour: the *last signal wins* regardless of source (OS change or panel click), which matches most app conventions (OS wins, user override wins back on next UI toggle).
- **Skip-link `.focus()` is programmatic, not href-default** — the anchor's default `click → navigate to #id` behaviour scrolls to the target but doesn't actually *focus* it. For SR + keyboard users, scroll-only is incomplete — the next `Tab` press continues from where focus was (probably the skip link itself), not the landmark. The click handler calls `element.focus({preventScroll:false})`, moving keyboard focus into the landmark. Landmarks need `tabindex=-1` so `.focus()` works on non-interactive container elements without adding them to the tab cycle.
- **Focus ring on every interactive via `:focus-visible`, not `:focus`** — Doc 24 §17.2 + Doc 16 §Focus Indicators call for "visible focus ring". Using `:focus` would show the ring on mouse click (visually noisy for sighted users). `:focus-visible` restricts it to keyboard-origin focus — the user agent determines when "keyboard or assistive-tech-ish" focus is happening vs pointer focus. Fallback `:focus:not(:focus-visible)` kills the outline for pointer-click for browsers that don't support `:focus-visible` gracefully.
- **FlyToAnimator `durationSec <= 0` means "snap", not "throw"** — the animator's `progress` getter divides `elapsedSec / durationSec`, which would produce NaN/Infinity for duration=0. Fix: constructor normalises to `1e-6` + pre-flags `state='finished'` so the very first `currentSample()` returns the end pose. Clean alternative would have been to add an `instant: boolean` flag, but existing callers already construct specs with arbitrary `durationSec`; a single negative/zero value stays within the existing API surface.
- **Controller fix for pre-finished animators** — the old `update()` check was `wasActive && !isActive` → `justFinished`. For a snap-to-end, `wasActive === false` from the get-go so this branch never fires, and the animator stays attached forever + `update()` keeps sampling the end pose. Added a parallel `preFinished = !wasActive && state === 'finished'` branch that also fires completion + drops the animator. Behaviour for normal fly-tos is unchanged (they start with `wasActive === true`).
- **SceneManager reads the setting at flyTo-dispatch time, not controller-construction time** — `useSettingsStore.getState().reducedMotion` is queried at the top of every `flyToEntity(...)` call. Toggling reduced motion mid-session applies to the *next* fly-to without rebuilding the controller. Alternative would have been to push the flag into the controller's state, but that couples the controller to the settings store unnecessarily.
- **High-contrast rules cascade via `[data-high-contrast="true"]` selector, not a `.high-contrast` body class** — dataset-attribute selectors read cleanly in DevTools + CSS, and the attribute namespace avoids collision with any `class="high-contrast"` the designers might want for an unrelated feature. Mirror is on `<html>` rather than `<body>` so the cascade kicks in before any React class-name computations fire.
- **CRT effects kept via settings toggle, not always-on until HC** — Doc 24 §17.6 calls for independent toggles for scanlines / pixel grid / flicker. Those already exist in `settingsStore` (`crtScanlines`, `phosphorGlow`). HC mode's cascade zeroes `text-shadow` + `backdrop-filter` + `box-shadow` app-wide, which takes down the phosphor glow + glass effects *without* needing to flip the individual toggles. When the user disables HC the effects come back automatically.
- **`target instanceof Element` guard around `.closest()` in the Escape handler** — `event.target` is the dispatched target, which is a `Window` when `window.dispatchEvent` is used (jsdom tests + the browser's document-level capturing). `Window.closest` doesn't exist → `TypeError`. `instanceof Element` narrows the type + safely short-circuits for non-Element targets. Caught by the test suite (AccessibilityPanel's Alt+A → Escape test).

### Post-processing chain + Schwarzschild lensing (T30)
- **One composite shader, many `#define` gates** — the Doc 18 §3.5 pipeline (bloom add → ACES → FXAA → CA → vignette → scanlines → grain) is packaged into a single fragment shader with `#ifdef POST_FXAA` / `POST_CHROMATIC_ABERRATION` / `POST_FILM_GRAIN` / `POST_VIGNETTE` / `POST_SCANLINES` gates. Flipping a feature at runtime rebuilds the defines + re-links the material (Three.js program cache keys on source + defines). Alternative was N separate materials on a per-feature basis; rejected because the uniform duplication across passes + the two extra full-screen draws per feature would have cost more than the re-link (which happens once per settings toggle — never per frame). Dynamic branching was also rejected: WebGL GPUs pay a real cost for `uniform float u_flag` gates inside the fragment hot path.
- **Custom 4-stage Gaussian pyramid, not `UnrealBloomPass`** — CLAUDE.md Rule #3 forbids importing from `three/examples/jsm/postprocessing`, so `PostProcessingChain` spins its own pyramid via (threshold → horizontal blur → vertical blur → downsample) per level, with iteration count driven by GPU tier (Doc 12 §2.1: high=5, mid=3, low=0). The exposed knobs (`threshold` / `strength` / `radius`) preserve parity with Doc 18 §3.5 values. Trade-off: ~30 extra lines of management code vs. pulling in a proven-working `UnrealBloomPass`; win is that we don't take a dependency on Three.js's examples folder (which changes signature across releases and has broken us before).
- **Function name collisions with Three.js built-ins** — first WebGL compile attempt fired `ERROR: 'luminance': function already has a body`. Three.js auto-injects utility functions (`luminance`, `linearToneMapping`, `ReinhardToneMapping`, `ACESFilmicToneMapping`, `sRGBToLinear`) from its `<common>` chunk even when the user frag doesn't use them. Fix: prefix every helper I define with `cosmos_*` (`cosmos_luma`, `cosmos_acesFilmic`, `cosmos_fxaaLuma`, `cosmos_fxaa`, `cosmos_chromaticAberration`, `cosmos_grainHash`). Single function name is enough — collision is per-name, not per-body.
- **Schwarzschild weak-field approximation, not full Kerr geodesic** — real multi-image / ergosphere / frame-dragging lensing requires a per-pixel ray-marched integrator over the metric tensor. The T30 pass ships `α ≈ 2 r_s / b` (Einstein 1916 weak-field result) applied as a single pull toward the impact vector in screen space, with horizon-disc early-out inside `r_s`. Result: stars + nebulae behind the BH curl around the horizon in a recognisable "gravitational curl"; correct to ≲1° for observers at realistic distance (10-100 r_s). Full ray-marched Kerr is a future task when profiling says we have the cycles.
- **Aspect-corrected impact parameter** — UV coordinates are anisotropic (wide-screen stretches the X axis). If we computed `b = length(offset_uv)` directly, off-axis BHs would get elliptical horizons. Fix: multiply `(uv - 0.5)` by `u_aspect = (w/h, 1)` before measuring `b`, then undo the correction when writing the UV offset (`uvShift = dir * alpha * (1 / u_aspect)`). Result: horizon is round regardless of viewport aspect.
- **Apparent angular radius computed CPU-side, not GPU-side** — could have uploaded world-space BH position + r_s and recomputed screen-space radius in the frag, but that's 4 BHs × fragcount matrix multiplies per frame. Cheaper to do it once per BH per frame on the CPU: `ndcRadius = schwarzschildRadius / (distance × tan(fov/2))`, package into the `Vector4.z` uniform slot.
- **Composite renders even when bloom is off** — the shader always samples `u_bloom`; the `u_bloomStrength` uniform gates the add to zero when bloom is disabled. Alternative was to write two composite shaders (with/without bloom) and swap, but the compile-time toggle of `POST_FXAA` etc. already demonstrates the shader-permutation cost; adding bloom to that list would have doubled the programs. Always-sample + zero-strength is one instruction of wasted work per pixel — trivial.
- **CRT scanlines in-shader, not CSS** — Doc 24 §3.5 spec locates scanlines on a CSS `::after` pseudo-element above the canvas but below the UI. Implemented here instead as `#ifdef POST_SCANLINES` inside the composite because (a) the in-shader frequency is defined in screen-pixels not CSS pixels → no retina moiré; (b) the HDR buffer's composited output is what the user sees and shader-layer scanlines line up with the ACES tone map — a CSS layer would darken the tone-mapped output unpredictably; (c) a single uniform controls both scanline density + phosphor-mask — easier to tune. CSS scanlines still render over the HTML UI layer; the shader version is on-viewport.
- **GpuLifecycleHook extracted to its own file** — the chain + lensing pass need the type to declare `implements GpuLifecycleHook`, but the hook's only definition lived in `SceneManager.ts`. Importing `type` would be a cycle (`SceneManager → PostProcessingChain → SceneManager`). Extracted to `engine/gpuLifecycle.ts` as a pure type file, with `SceneManager.ts` re-exporting it for backwards compatibility so the 8 existing renderer imports keep working unchanged.
- **Auto-register exotic gallery BH** — `?demo=exotic` was the obvious smoke-test demo for lensing (gallery already had a black hole). Added `ExoticGalleryRenderer.getBlackHoleTransform()` that returns world position + apparent radius (0.3 × scale, matching the shader's `u_horizonRadius` default); SceneManager calls it after constructing the post chain and registers one handle. Zero code churn for non-exotic demos (gallery is null → no-op).
- **Reduced-motion pins grain seed to 0, doesn't disable film grain entirely** — Doc 16 §Reduced Motion says "disable bloom/glow" is an a11y option, but disabling grain entirely changes the image's texture character (flat vs. filmic). Pinning the seed so grain doesn't animate is the compromise: the static grain texture is still present but doesn't flicker, which is the actual motion-induced a11y concern. Full grain-off is still available via `filmGrain: false` toggle.
- **Preview smoke verification via uniform readouts + GL-state introspection** — consistent with T28/T29 gotchas (`preview_screenshot` times out on the live chain). Asserted correctness via `eng.blackHoleLensing.getMaterial().uniforms.u_blackHoles.value[0].toArray()` (the 4-float packed vector), `eng.renderer.getContext().getError()` (0 = no WebGL state error), and `eng.renderer.info.programs.length` (9 programs compiled = scene materials + 4 post-chain passes). Stale console errors from my first compile attempt (`luminance` collision) show up in `preview_console_logs` but are historical — the live state has `cosmos_luma` in the fragment source (verified via `pp.getThresholdMaterial().fragmentShader.includes('cosmos_luma') === true`).

### Galaxy shaders + cosmic web + CMB (T29)
- **One frag per morphology, not unified `#define`** — same call as T27 nebulae / T28 exotics. Spiral's spiral-arm mask, elliptical's Sérsic ellipsoid, irregular's spatial-hash clumps, and lenticular's ripple disk diverge at the first sample; packing all four into a single `#ifdef GALAXY_*` frag would leave ~70% dead code per permutation and the TS-VQA-004 ΔE assertions would be unreadable.
- **Galaxy as volumetric raymarch cube, not particle system** — Doc 18 §LOD System 0 says "volumetric particle cloud", but a particle system means O(100K) points per galaxy × 4 galaxies in the gallery — way past the 500-draw-call budget. Raymarching a unit cube is one draw call per galaxy regardless of internal detail; the fbm density field simulates the particle population visually without the geometry cost. Real particle-cloud LOD can slot in later as an alternative `GalaxyLodTier` once profiling says we have the cycles.
- **Logarithmic-spiral with `tan(pitch)`, not `cot(pitch)`** — Doc 22 ENT-6010 §Spiral flagged the `cot` variant as an error ("should be r = r₀ exp(θ × tan(pitch))"). I used `θ_arm(r) = log(r) / tan(pitch)`; correct for the standard form. Pitch default = 18° matches Doc 22 (range 12–26°).
- **LOD as three tiers, not Doc 18's five** — LOD0-4 in Doc 18 §LOD System ranges from "volumetric particle cloud" to "single billboard with galaxy icon". LOD1 (high-res disk texture) and LOD2 (medium-res disk, arms visible) are indistinguishable without real texture assets, and LOD3 (single sprite) + LOD4 (icon) differ only in the glyph. Collapsed into 3 tiers — volumetric / billboard / point — the gallery demo stays readable and the TS-VQA-005 SSIM baseline isn't muddled by intermediate texture fidelity.
- **Billboard as camera-facing quad with radial tint gradient, not textured sprite** — ENT-6010's default LOD4 palette/tint is all we need for the distant appearance; the radial exp falloff reads as a galaxy glob from any angle. Adds one 2-tri draw call per galaxy at the billboard tier and retains GLSL-only CLAUDE.md Rule #1 compliance.
- **Gallery-space LOD breakpoints (260u/900u), not defaults (60u/200u)** — preview-smoke verified that the SceneManager's camera-pullback of (0, 6, 90) puts every galaxy ~130u away, past the default 60u volumetric cap. Rather than move the camera closer and compress the row, I widen the breakpoints inside the gallery renderer only. Production galaxy instances keep the tight defaults so the LOD picker actually engages.
- **Cosmic web as TubeGeometry + LineSegments wireframes, not volumetric raymarch** — filaments are thin tubes by nature; Catmull-Rom spline → `THREE.TubeGeometry` gives faithful 3D geometry at ~200 tris per filament × 10 filaments = 2000 tris budget. Voids as icosahedron-edge wireframes (`EdgesGeometry` → `LineSegments`) render as subtle dashed-sphere outlines at near-zero cost. Volumetric marching every filament would blow the draw-call budget for a static structure that doesn't benefit from the internal fbm detail.
- **CosmicWebRenderer takes explicit node/filament/void specs, NOT a procedural generator** — Doc 17 §ENT-7030 describes "linear or gently curved chains of galaxy clusters"; the DEFAULT_COSMIC_WEB constant encodes the Local/Virgo/Coma/Perseus/Sculptor/Hercules/Abell/Tail topology as a hand-authored graph. Keeps the rendering deterministic for TS-VQA-007 pHash and lets the ETL-driven mesh override the defaults later via `cosmicWebOptions` without touching the renderer.
- **CMB as inward-facing IcosahedronGeometry + procedural fbm**, not a Planck texture map — Doc 18 §Cosmic Microwave Background describes loading Planck/WMAP equirectangular texture; shipping without the texture asset drops a future binary dependency and keeps CLAUDE.md Rule #1 clean. Two-octave fbm (ℓ~2-40 at large scale + ℓ>200 speckle) produces the characteristic splotch pattern at the resolution the observer sees; the real texture swap is one uniform change later.
- **CMB radius 800u, not 1e14u** — Doc 10 §3 sets camera far plane to 1e14 which would let us park the CMB at the horizon of the observable universe. But the scene's galaxies sit at z=-40 and the cosmic web spans ±50u; a CMB at 1e14 would be invisible without extreme camera pull-back. 800u sits well outside the galaxy/web meshes, small enough to be seen while the camera is anywhere inside the (default) 1u-5000u range, and the log-depth buffer resolves the scale ordering without z-fighting.
- **Andromeda distance = 778 kpc, not 780 kpc** — Doc 23 §17.3 quotes "780 kpc", Doc 30 TS-DATA-002 says "778 kpc ± 33 kpc". I use 778 to match the test expectation exactly; the 2 kpc difference is well inside the ±5% band in either direction. NED consensus + Riess 2019 Cepheid/TRGB averages both support 778 kpc. Revisit when a real catalog ingestion ships.
- **TS-DATA-005 all-9-categories rollup lives in the galaxy-catalog test** — the CLAUDE.md 9 categories are: stars, rocky planets, gas giants, moons, small bodies, nebulae, galaxies, large-scale structure, exotic. The test walks SOLAR_SYSTEM_CATALOG (stars/rocky/gas/moons/small-bodies), `NEBULA_KINDS` (5 nebulae), `GALAXY_CATALOG` (12 galaxies), `EXOTIC_KINDS` (3 exotics), and counts the cosmic web + CMB as large-scale-structure exemplars (non-zero by construction). Each category has ≥1 exemplar → TS-DATA-005 green. Live in galaxyCatalog.test since that's the last module pulling all the others' types together.
- **Preview-screenshot timeout, uniform-readout verification** — `?demo=galaxies` preview_screenshot timed out 2× in a row but `preview_snapshot` shows the canvas live, and preview_eval reports `renderer.info.render.calls=6` + `tris=60` + correctly-computed `u_cameraLocal` (= `(camWorld - meshWorldPos) / meshScale`). Per the existing T28 gotcha ("Preview rAF throttles to ~1-2 fps headless") the screenshot loader can race the GPU swap; text-based verification via uniform + draw-call counts is the authoritative proof.

### Scale-regime state machine (T25)
- **Pure controller, side-effects at the call site** — `ScaleRegimeController` takes a scalar (AU from the Sun) and emits transitions via a callback. It touches no stores, no tile manager, no DOM. The SceneManager's transition handler does the plumbing (`cameraStore.setScaleRegime`, `tileStreaming.setActiveRegime`, `onRegimeChanged` forward). Pays off in tests: the controller is exercised with plain numbers in a tight loop — 100 iterations of a hysteresis bounce runs in sub-ms, no act()/fake-timers/module-mock machinery.
- **One rung per `update()`** — a teleport to cosmic distance while sitting in solar_system walks solar_system → stellar on the first call. Second call promotes stellar → galactic, third to cosmic. Alternatives considered: (a) walk the ladder until stable inside one call — rejected because it couples the controller's clock to the caller's (a single wheel-tick at 1e9× fly-out would fire 3 transition events on the same frame and the UI would see "solar_system" and "cosmic" back-to-back in one animation step, with no cinematic transition). (b) jump straight to the final regime — also rejected because Doc 19 §ScaleTransitionAnimations treats each rung as a separate cinematic. One-rung-per-call preserves the per-rung animation hook point for T26/T27. In practice 60 Hz resolves teleports within 2-3 frames which is imperceptible.
- **Hysteresis as `{enter, exit}`, not `threshold ± band`** — same information, different ergonomics. Stellar's `enter = 500 AU` and `exit = 400 AU` make the invariant `exit < enter` visually obvious in the code, and the "are we transitioning now?" branch is a single comparison per direction. The `± band` form would require two additions every predicate call.
- **Distance-from-Sun ≈ distance-from-MW-centre at Mpc scale** — the Sun sits 8 kpc from the galactic centre; the galactic→cosmic hysteresis band is 200 kpc (25× the offset), so using distance-from-Sun as the input is accurate to <1% of the band. Saves plumbing a second vector through every frame. Revisit if a future observation mode anchors the camera to a non-Sol reference.
- **Scene-unit ↔ AU conversion lives in SceneManager, not the controller** — the renderer's `orbitScale = 12 units/AU` is a display-scale fudge (T14 decision, reverts in T26 when strict 1:1 km lands). Doing the conversion at the call site means the controller never sees the fudge; flipping to strict scale in T26 is a one-character edit in `SceneManager.publishCameraState` (`12` → `AU_KM`). Controller stays correct.
- **Seed `tileStreaming.activeRegime` from `controller.current` at ctor** — without this seed, the tile manager would enqueue freely until the first regime transition fires. The default regime is `solar_system`, which admits zero tile kinds; seeding means pre-transition tile_priority WS frames are rejected exactly as they would be post-transition. One fewer edge case for T26 to explain away.
- **Transition prunes queue but not in-flight** — when the regime changes, `setActiveRegime` drops queued (not dispatched) addresses whose kind doesn't match the new regime. In-flight fetches are left alone: bandwidth has been spent; the tile store will still accept the response; the only cost is a tile that sits unused for a few frames before LRU eviction kicks in. Aborting mid-stream saves no network work (TCP windows are already committed) and loses the Brotli cost we already paid. Cheap side-effect > perfect purity.
- **`isAddressRelevantForRegime` returns `true` for unknown prefixes** — forward-compat. When T-later lands CMB tiles (`cmb/0`) or custom FITS render tiles, the filter defaults to "let it through" rather than silently swallowing them. The per-regime set is a *positive* whitelist over the current tile families, not a *negative* blacklist. Adding a new tile family is one edit in `REGIME_TILE_KINDS` — not a hunt for every filter callsite.
- **Preview smoke pattern for regime transitions** — preview_eval imports are module-instance distinct from the bundle's (confirmed again), so we can't `import('…/ScaleRegimeController').ScaleRegimeController` and drive the SceneManager's instance. Solution: call `eng.scaleRegime.update(distAU)` on the live instance + replace the onTransition handler to append to an array (then re-replace after to restore SceneManager's default path). Tile filter exercise: set regime, enqueue mixed kinds, read `getRegimeFilteredCount()` delta — no DOM assertion needed. Logged rejected counts of 3 / 2 for solar_system / stellar match Doc 27 §9.3 exactly.

### Tile server (T24)
- **Filesystem store now, DB later** — Doc 25 §7.1 describes the prod flow (Redis → SSD / Object Storage → Brotli → cache write-through). For T24 the in-tree `TileStore` impl reads from a filesystem root (`<root>/stars/z/x/y/level.bin`, `<root>/galaxies/idx.bin`, `<root>/cosmic-web/sector.bin`). That's exactly what the Airflow ETL (T-ETL) writes to and what an object-storage mount projects into. Swapping to Postgres/S3/Redis later is a trait impl, not a handler rewrite. Zero schema coupling means tests don't need Postgres containerised either.
- **Trait, not struct** — `pub trait TileStore: Send + Sync + 'static`, async methods via `#[axum::async_trait]`. `Router::with_state(Arc<AppState { store: Arc<dyn TileStore> }>)` lets a test swap in a mock impl for fault injection (e.g., simulate a disk I/O storm) without reaching for mock-fs or the filesystem at all. Sibling benefit: `AppState` no longer derives `Debug` because `dyn TileStore` doesn't, so a manual impl shows `"<dyn TileStore>"` for diagnostic tracing without forcing every future backend to carry `Debug`.
- **Address validation lives in the store, not the handler** — the handlers parse path params (axum `Path<(u32, u64, u64, u32)>`) and hand them off. Only the store can reject `z=9`/`level=4`/`healpix_idx=786432`/`sector=64` with `TileError::InvalidAddress`, because only the store will ever have the full address context. This also means the validation logic is exercised by store unit tests directly, not by spinning up the router. `x,y` use `u64` (not `u32`) because `8^z` at z=8 is 16 777 216 — well within u32 but an extra factor of safety when someone inevitably tries z=9 + a ludicrous coord; we reject the z first anyway.
- **`8^z`, per Doc 26 §7.1, not `2^z`** — the doc says x,y ∈ [0, 8^z). A traditional octree has 2^z per axis, not 8^z. We follow the doc literally — the stricter cap is TILE_NOT_FOUND at the filesystem layer anyway, so the validation is mostly about rejecting garbage input cheaply. If the ETL or the spec ever resolves to 2^z, flipping the constant is one character.
- **Brotli compression is a layer, not a per-route concern** — `tower_http::CompressionLayer::new().br(true)` negotiates `Content-Encoding: br` transparently based on the client's `Accept-Encoding`. Octet-stream + json both qualify by default. No handler ever calls a compressor. Tests use `Accept-Encoding: identity` so they can assert on raw bytes; the integration test for compression is the live curl smoke (`content-encoding: br` present, `struct.unpack` on the decompressed body matches fixture).
- **Envelope errors are own module, not ad-hoc `(StatusCode, Json<…>)`** — `TileError::into_response` is the single serialisation point for Doc 26 §15. Handler signatures are `Result<Response<Body>, TileError>`; the `?` operator makes every fallible store call auto-convert. `Cache-Control: no-store` stamped on every error so CDN layers can't cache a transient 500 or a misbehaving 404. `X-Request-ID` generated per-error (we don't plumb the incoming request id into the error path yet — a tracing middleware is the right home for that, not the error type; future T).
- **Manifest ETag = `W/"{version}"`** — weak ETag because the server doesn't guarantee byte-identical representation (JSON whitespace / key ordering can drift). Clients compare on semantic equivalence, which is what `If-None-Match` revalidation wants. Version is pulled from the payload's `data.version` / `version` field first (what the ETL will write); falls back to `COSMOS_DATA_VERSION` env var (what fresh dev environments have). No ETag on binary tiles — they're already `immutable`, so revalidation is pointless; the CDN and browser treat the `max-age=86400` + `immutable` combo as "never re-fetch until the URL changes."
- **`X-Tile-{Star,Galaxy,Vertex}-Count` parsed from the first 4 bytes** — cheap (no full decode) and gives the tile streaming manager a way to reject truncated responses before decoding. We read `u32` at offset 4 for stars (after `tile_id`), offset 0 for galaxies and cosmic-web. If the buffer is shorter than 8 bytes we skip the header — same safety the T23 decoder applies. Not worth a full parse + serialise round trip; the real verification happens client-side in `decodeStarTile`.
- **axum 0.7 Router state typing** — `Router::new().nest("/v1", subrouter)` requires matching `S` types on outer and nested routers. Tried that; compile error because outer starts as `Router<()>` while nested is `Router<Arc<AppState>>`. Rewrote to a flat route list with absolute paths (`/v1/tiles/…`) then a single `.with_state(state)` at the end. Simpler, one fewer type annotation to babysit.
- **`Router::oneshot` beats `reqwest` for tests** — `tower::ServiceExt::oneshot(app, req)` calls the router synchronously (modulo async) without starting a TCP listener, picking a port, or threading a reqwest client. Tests run in single-digit ms; `cargo test` passes 18 tests in 11 ms total (the 12 s was mostly the Rust 1.94 clean compile; incremental builds finish in under 1 s).
- **Removed the stub's sqlx + redis dependencies** — original scaffold pulled them in "for future use" but they cost ~2 minutes off every CI cold build. ETL/Redis work slots them back in later. Keeping the Cargo.toml lean until there's a consumer pays off.

### Live ephemeris (T21)
- **Sampler, not per-body fetch** — the renderer calls `sample(naifId, jd)` every frame for 13 heliocentric bodies. Hitting `/ephemeris/{id}` per-frame (even at 60 Hz × 13 bodies = 780 req/s) blows past the Research tier's 1,000 req/min and burns SPICE compute. Pre-fetching a 730-day window per body via `/ephemeris/range` → Catmull-Rom interp collapses network load to one fetch per body per window, and keeps animation silky.
- **Cubic over linear** — linear interp on a 1-day step gives ~5,500 km chord error for Earth (ω²·r·dt²/8 at mean motion 0.0172 rad/day). Catmull-Rom on the same step gives ~3 m. Spec says "sub-km accuracy"; cubic lets us keep step=1 day (stays under the 10,000-sample/fetch cap) instead of forcing 0.005-day steps.
- **Planets only, not moons** — catalog moon elements are encoded in the parent-equatorial frame (Doc 23 §8.5), but `/ephemeris/range` defaults to ECLIPJ2000. Routing moons through the sampler without a parent-pole rotation would drift them off the Kepler positions they've always used. Moons stay on Kepler until the T27 per-moon-shader pass, where we'll add the parent-equatorial ↔ ecliptic transform.
- **Silent fallback > loud errors** — `sample()` returns `null` for *any* unavailable sample (cache cold, out of window, in-flight, errored, throttled). Renderer always has Kepler in its pocket. No spinners, no modal notifications — if the backend is down the user just gets T14 accuracy silently.
- **Generation-counter guards stale resolves** — a slow first fetch can resolve AFTER a later prefetch has already filled the cache. Without the guard we'd overwrite the fresher data with stale results. Each `startFetch` bumps `entry.fetchGeneration`; resolves compare before writing.
- **Retry backoff = 30 s per body** — aggressive enough that a momentary upstream blip self-heals within a user's attention span, conservative enough that a dead backend doesn't spam 13 req/s. The `nextRetryAt` gate is wall-clock (`Date.now`), so an `error` → `error` cycle doesn't burn quota.
- **Throttle above 365 sim-days/s** — `setPlaybackContext` feeds the sampler `playbackSpeed/86_400`. At 1e9× speed the simulation burns a 730-day cache in ~60 ms of wall time; every sample would be out-of-window, every sample would trigger a refetch, and the cache would never stabilise. Above the threshold `sample()` short-circuits to `null` and Kepler takes over. Below the threshold sampling auto-resumes — no manual state toggle.
- **Module-scope log dedupe across bodies** — 13 bodies × 1 error each, warned once per body per error cycle. Vite HMR reloads reset the set (expected). Single hard load = 13 warns max, not 13·N where N is frame count.
- **Moon list exclusion via renderer method** — `getHeliocentricBodyIds()` walks `this.planets ∪ this.dwarfPlanets` (excludes `MAJOR_MOONS` + `SUN`). SceneManager uses it instead of re-importing the catalog, so the catalog stays the single-source-of-truth for "what's heliocentric".
- **Preview-eval swap test pattern** — per-module-instance gotcha still applies, so I swapped the whole sampler rather than mutating `apiConfig.fetchImpl`. A duck-typed `{ sample, setPlaybackContext }` fed through `setEphemerisSampler` is enough to prove the render loop reads from the sampler — no class import needed. Verified Earth lands at scene (60,0,0) = 5 AU × orbitScale and `getLastLiveHitCount()=1`.

### Tracking (T20)
- **Δ-shift, not absolute-lerp** — apply the body's per-frame Δ-position to both `target` and `camera.position`. This preserves the spherical offset exactly, so the user's orbit pose (θ, φ, r) is an invariant of the body frame. Alternative would be to re-target-lerp each frame, but that collapses the orbit radius and forces the camera forward every frame.
- **Baseline-on-change, not baseline-on-call** — `syncTracking` is called every frame regardless, so the naive "always anchor = current pos" would zero every delta. We anchor only on the first call after `id` changes (or anchor is null), then apply deltas from that anchor on every subsequent same-id call. Re-enabling tracking on the same body after a disable cycle re-baselines cleanly.
- **Shift target AND camera.position** — controls.update() recomputes `camera.position = target + sphericalOffset`, so shifting target alone gives the right final pose. But callers (tests, UI probes) may read camera.position between syncTracking and controls.update; shifting both keeps mid-frame reads consistent and lets the math be asserted from two angles in unit tests.
- **Fly-to takes precedence** — while `isFlyingTo()`, syncTracking re-baselines the anchor but does NOT shift. Fly-to owns the camera; on arrival, the anchor has already absorbed the latest body position so the first post-arrival tracking frame applies zero delta and subsequent frames shift normally.
- **Frame order: time → solarSystem.update(jd) → syncTracking → controls.update → publish** — tracking needs the body's CURRENT-frame world position, so the solar-system renderer must advance BEFORE the controller. Previously solarSystem.update ran last (after render), but nothing read its output in the same tick. Reorder is safe.
- **Starting fly-to clears tracking of a DIFFERENT body** — if `trackedEntityId` ≠ fly-to target, drop it; can't fly to X while tracking Y. If they match, keep tracking on so it resumes seamlessly post-arrival. Explicit flag change, not implicit.
- **Tracking survives `clearSelection`** — closing InfoPanel doesn't disable tracking; user may want to free-fly while camera is anchored to a body. Downside: no global HUD indicator yet — user must re-select the body to reach the Track button. Future HUD chore.
- **`setTrackedEntity(id)` returns `false` for bodies not in scene** — guards against stale selections from search results outside the solar-system catalog. Returns `true` for `null` (disable is always valid).
- **InfoPanel footer reshuffled to 2×2** — was `[Navigate][Bookmark][Share]` single row; now row 1 = primary (Navigate + Track), row 2 = placeholders (Bookmark + Share disabled). Green accent for Track matches the "moon" category colour but stands out against the pink Navigate.
- **Preview verification via direct engine calls, not store evals** — the gotcha from T19 holds: `import('/src/stores/cameraStore.ts')` in preview_eval is a different module instance than the running bundle. Reading `useCameraStore.getState().trackedEntityId` after calling `eng.setTrackedEntity(id)` returned null; had to read `eng.controls.getTrackedId()` instead. Similarly, `useTimeStore.getState().pause()` in eval is a no-op; to crank playback speed use the TimeControls slider's native-setter + `input` event (which DOES route through React → the bundle's timeStore).

### HTTP client (T18)
- **Single `apiConfig` module** (baseUrl / apiKey / etagCache / fetchImpl) — no store coupling. Tests swap `fetchImpl` without monkey-patching `globalThis.fetch`. Dev-bound `globalThis.fetch` captured once at init; callers overriding `window.fetch` after that will not be seen — must route through `apiConfig.setFetchImpl`. Learned via preview smoke.
- **Envelope unwrap in one place** — `apiGet`/`apiGetCollection`/`apiPost` always return `.data` (item) or `{items, pagination}` (collection). Callers never see `{ data, meta }`.
- **`ApiError` classification: `.code` + `.status` + `isRetryable()` / `isNotFound()`** — callers decide fallback vs surface vs abort. `NETWORK_ERROR` for fetch rejections + unparseable bodies.
- **Retry policy = Doc 27 §15.3**: 429 honours `error.retry_after_seconds`, 5xx/502/503/504 + NETWORK_ERROR exponential backoff capped at 2 s. Non-retryable 4xx throws immediately. If-None-Match dropped on retry (server may rotate etag).
- **Two cache layers** — (1) client ETag cache (keyed by URL, transparent 304 revalidation, skipped on `bypassCache: true`); (2) entities LRU 500-entry, cross-indexed by numeric id + ent_id so `getEntity(42)` and `getEntityByEntId('ENT-1042')` share a row. `/ephemeris/*` bypasses both (epochs rarely repeat, ETag just adds a hop).
- **Local validation before network** — `getEphemeris` / `getEphemerisRange` reject bad NAIF ids (< 0) + out-of-range epochs (JD [2 287 184.5, 2 688 976.5]) as `ApiError` before a hop. `postEphemerisBatch` defers to the T11 `validateBatchEphemerisRequest` → `BatchEphemerisError`. Keeps the server free of client-bugs-as-traffic.
- **Selection upgrade is optimistic** — `selectEntityAsync(id, optimistic)` seeds client-side synthesis (`bodyToEntity`) instantly for zero-latency UI, then fetches `/solar-system/bodies/:naifId` and swaps to the authoritative payload. If the user clicks a different body mid-flight, the stale response is dropped by `selectedEntityId !== id` guard. Fetch errors keep the optimistic data on-screen and populate `selectionError`.
- **Adapter owns the payload shape** — InfoPanel didn't change a prop; `apiSolarSystemBodyToEntityData` produces the same `payload.*` keys `bodyToEntity` does. Adds `source: 'api:solar-system' | 'api:entity' | (undefined=catalog)` so the dev line reveals provenance.
- **Dev proxy `/v1 → localhost:8080`** — same-origin in dev, no preflight. `VITE_DEV_API_TARGET` env override for tunnelled staging. Prod env `.env.production` points at `https://api.cosmosexplorer.app/v1` (Doc 26 §2.1).
- **`@cosmos/api-client` workspace package left empty** — originally earmarked for OpenAPI-generated code; hand-rolled types live in `apps/web/src/api/types.ts` faithful to Doc 26. Generator swap is a future task; no consumers lock into `@cosmos/api-client` yet.

## Gotchas

### Shaders + WebGL
- `#version 300 es` in shader source breaks Three.js GLSL3 (duplicate after injection). Omit it.
- `THREE.Material.needsUpdate` / `BufferAttribute.needsUpdate` are **setter-only** — assert via `.version` increment.
- `WEBGL_lose_context.restoreContext()` doesn't always fire `webglcontextrestored` immediately after `loseContext()`. Real driver resets fire normally.
- `u_sunDir = (1,0,0)` puts terminator head-on for a `+Z` camera. `(0.6, 0.25, 0.75)` = lit hemisphere with shape cues.
- `THREE.RingGeometry` is XY plane; Saturn's equator is XZ — rotate ring mesh `−π/2` around X.
- ICRS ecliptic is +Z-up; Three.js is +Y-up. Map `(X,Y,Z)_icrs → (X, Z, −Y)_scene`; any raw-vs-scene test must apply the permutation.
- **Log-depth define renamed in Three.js r184**: it's `USE_LOGARITHMIC_DEPTH_BUFFER`, NOT the old `USE_LOGDEPTHBUF`. Custom `ShaderMaterial` that writes `gl_Position.z/w` without emitting `gl_FragDepth = log2(vFragDepth) * logDepthBufFC * 0.5` mixes non-log depth into a log-depth buffer, so built-in materials (Sun's `MeshBasicMaterial`, star points, orbit lines) that DO emit log depth test against the wrong encoding → opaque objects behind fail the test and appear on top. Fix: inject `#ifdef USE_LOGARITHMIC_DEPTH_BUFFER` blocks in `planet.vert`, `planet-rocky.frag`, `planet-gas.frag`, `ring.vert`, `ring.frag`, `star-point.vert`, `star-point.frag` with `out float vFragDepth` in vertex + `uniform float logDepthBufFC; in float vFragDepth;` + `gl_FragDepth = log2(vFragDepth) * logDepthBufFC * 0.5;` in fragment. Three.js auto-uploads `logDepthBufFC` when the uniform is declared. Verified by dumping `gl.getShaderSource(gl.getAttachedShaders(program)[1])` and checking for `#define USE_LOGARITHMIC_DEPTH_BUFFER`. Symptom that triggered the fix: Sun visibly bleeding through Earth when camera is placed on the far side of the planet.
- **Three.js auto-injects `luminance` + other `<common>` helpers into every fragment shader** — user shaders that define `float luminance(vec3)` hit `ERROR: function already has a body` at compile time (WebGL validate step, not Three.js itself). Other landmines: `linearToneMapping`, `ReinhardToneMapping`, `ACESFilmicToneMapping`, `sRGBToLinear`, `packNormalToRGB`, `unpackRGBToNormal`. Fix: prefix every user-defined helper with a project-specific namespace (e.g. `cosmos_*`). Discovered during T30 post-chain preview smoke — first compile attempt of `post-bloom-threshold.frag` fired the error; rename + function call-site edits resolved.

### Float precision + physics
- `3.0857e16 + 1 === 3.0857e16` — float64 can't resolve 1 m at parsec scale. Motivates Doc 23 §3.4 hierarchical frames (T23).
- `Math.sign(0) === 0` — explicit branch in `solveKepler` avoids Danby seed drift at M=0.

### Store + engine
- Zustand `setState({ position })` replaces wholesale — new reference each frame. UI must use equality selector or 100 ms throttle.
- `CameraController` snapshots spherical coords at construction. Post-ctor `camera.position.set()` silently reverts — call `controls.setTarget(...)` to resnap.

### SPICE
- `spice.furnsh` is process-global + ref-counted. Pytest session fixture owns `kclear()`; FastAPI lifespan must NOT clear or it trashes the test pool.
- SPICE raises dynamically-named exceptions; no typed base. Catch `SpiceyError` + classify by `exc.short`.
- Python 3.14 local / 3.11 Docker — both get SpiceyPy wheels; no version-gated features.

### jsdom + preview
- jsdom 24 missing `PointerEvent` + `canvas.getContext('2d')` returns null on Windows. Polyfills in `engine/__tests__/setup.ts`.
- Vite dev: `import('/src/x')` vs `import('/src/x.ts')` are **different module instances**. Diagnostic evals must use `.ts`.
- Preview rAF throttles to ~1–2 fps headless. Drive engine manually (`controls.update`, `timeEngine.update`); `PerformanceMonitor` reads `fps: 0` — confirm liveness via position-delta, not FPS.
- `gl.readPixels` on default framebuffer returns black after browser composite (`preserveDrawingBuffer: false`). Use `preview_screenshot` for ground truth, not `readPixels`.
- Portrait aspect crops horizontally — don't tune frame composition to landscape only.

### TypeScript
- TypeScript rejects `0x_4C4F53_41` — numeric separators only between hex **digits**, not adjacent to `0x`.

- **T38 live-ingest bug-catch ledger** — 5 bugs that ALL offline tests (pytest, alembic `--sql`, mock ES) missed; only real Postgres 16 + PostGIS 3.4 + ES 8.12 containers surfaced them. (1) `to_tsvector(regconfig, text)` is STABLE not IMMUTABLE → `GENERATED ALWAYS AS STORED` rejected; use a trigger-maintained column. (2) `ent_id VARCHAR(10) UNIQUE` is semantically wrong — Doc 17 ent_id is a *subtype* label (29 Messier globulars share ENT-7011); drop UNIQUE, enforce object-level uniqueness via `cross_identifications`. Always pass the full optimistic payload to `selectEntityAsync`, not a separate pre-call. **Lesson:** unit tests protect against regressions; only live integration catches schema-level and wire-shape mismatches. Keep a "live smoke" verify step in every ETL task's gate.
- **Scale-regime × renderer coupling** — enabling `showStarField` forces `scaleRegimeOptions.initial = 'stellar'` (via `CosmosCanvas.tsx:88–92`), which uses AU-scale factors orders of magnitude larger than 'solar_system'. - **`ent_id` is a subtype, not an object key** — Doc 17 ent_id `ENT-NNNN` identifies a rendering subtype (ENT-7011 = globular cluster). Multiple physical objects share the same ent_id (29 Messier globulars, 26 Messier opens, 11 Virgo galaxies).
